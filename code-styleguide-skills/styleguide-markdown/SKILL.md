## 目标

基于 Google Markdown style guide，为 Markdown 文档提供**可执行**的风格约束，用于：

- 文档评审：快速识别结构、标题、列表、代码块、链接与表格等可维护性问题。
- 降低维护成本：保持“源文本可读、可移植、易于长期维护”。
- 输出建议：将规则落为“检查点 + 最小示例”，避免背诵式长文。

## 规范来源与优先级

1. 项目/团队约定（仓库内已有文档规范或 lint 规则时优先）。
2. 本 Markdown skill（本文）。
3. Google Markdown style guide（官方原文）。

当冲突或无法确定时，默认选择：**更易读、更可维护、更接近现有文档库风格**的一侧，并说明理由。

## 核心目标（用来裁决“可选项”）

1. 源文本可读且可移植（plain text 友好）。
2. 文档长期可维护（跨团队/跨时间一致）。
3. 语法简单易记（避免花式写法与 HTML hack）。

## 核心检查清单（可执行）

### 文档布局（Document layout）

推荐结构：

- 文档标题（H1）
- 1–3 句简介（说明是什么/为什么/读者是谁）
- 可选 `[TOC]`（若文档较长）
- 从 H2 开始的正文分节
- 末尾 `See also`（可选，放杂项链接）

### 标题（Headings）

- **只用 ATX 风格标题**：`#` / `##` / `###`，不使用 `====` / `----` 下划线标题。
- **只使用一个 H1**：作为文档标题；后续从 H2 开始。
- **标题要唯一且完整**：避免重复的“Summary/Example”这类标题，必要时加前缀让锚点可读（如 “Foo summary”）。
- **标题前后留空行**：标题前后各有空行，且 `## Heading` 的 `##` 后必须有空格。

### 行宽与换行（Character line limit）

- 通常遵循 **80 字符行宽**（便于代码搜索与工具链处理）。
- 例外：链接、表格、标题、代码块。
- 包含链接的行：**链接本身可很长**，但链接前后的文字应合理换行。

### 末尾空白（Trailing whitespace）

- **禁止行尾空白**。
- 不用“行尾两个空格”制造 `<br>`；如确实需要换行，用**行尾反斜杠**（谨慎使用），或更推荐改写为段落/列表。

### 列表（Lists）

- 长编号列表优先用“懒编号”（全写 `1.`）以减少维护成本；短列表可用完整编号。
- 嵌套列表缩进规则：
  - 推荐统一使用“内容列对齐”的缩进（常见做法：子层相对父层内容列再缩进 4 空格）。
  - 列表换行的后续行同样按内容列对齐缩进，保持源文本可读。
- 小而不嵌套的列表可用单空格缩进，但同文档内保持一致。

### 代码（Code）

- **内联代码**：引用文件名、字段名、命令、短路径等使用反引号：`README.md`、`foo_bar`。
- **代码块**：
  - 优先使用 fenced code block（```），不要用 4 空格缩进代码块。
  - 尽量声明语言（如 ```shell / ```bash / ```json / ```java）。
  - 命令行示例若跨行，建议使用 `\` 续行以便复制粘贴（特别是 shell 命令）。
- 列表中嵌套代码块：代码块需要额外缩进以不打断列表结构。

### 链接（Links）

- **避免裸 URL**：优先使用带语义的 Markdown 链接文本，而不是 “here/link” 或直接贴 URL。
- 尽量缩短长链接；长链接/重复链接可用 reference links：
  - reference link 的定义建议放在**首次出现的同一节末尾**（下一个标题前），或若跨多节复用则放文末。
- 文档内部链接优先用明确路径；跨目录尽量避免 `../` 形式的相对路径（除非同目录内）。

### 表格（Tables）

- 仅在确实需要二维扫描对比时用表格；能用列表表达就用列表。
- 表格内容尽量短；长链接建议用 reference links。

### HTML（Strongly prefer Markdown to HTML）

- **强烈优先 Markdown**，避免 HTML hack；如果必须用 HTML，先反思是否真的需要（除非大型表格等场景）。


## 工程化落地（Workflow）

- **本地一致性**：提交前至少执行格式化与静态检查，避免仅在 CI 暴露风格问题。
- **CI 守门**：将风格检查作为必过项；格式化工具输出与审查结论冲突时，以团队约定优先并在 PR 说明。
- **渐进整改**：遗留代码按“触达即治理”原则处理，优先修复当前变更范围内的风格/可读性问题。

## 常见冲突与处置

- **规范冲突**：优先级始终为“项目约定 > 本文 > 官方参考”。
- **工具与人工结论冲突**：优先保证可读性与一致性，并在评审中记录取舍理由。
- **增量与全量冲突**：优先保证本次修改范围一致，避免在无关区域引入大规模格式噪音。

## 最小示例

```markdown
## 标题

- 条目一
- 条目二
```

## 工程化命令（本地/CI）

- 本地：`prettier -w "**/*.md"`
- CI：`prettier -c "**/*.md"`

## 本 skill 的回答方式（输出模板）

当用户给出 Markdown 文档/片段/问题描述时，按以下结构输出：

1. **适用范围判定**：Markdown + 涉及点（标题/列表/代码块/链接/表格/行宽等）。
2. **结论（3–10 条检查点）**：逐条对应本规范条目，优先指出“会降低可维护性”的问题（重复标题、行尾空白、裸链接、缩进混乱等）。
3. **最小示例**：只给必要的 before/after 对照（保持改动小且聚焦）。
4. **不改语义声明**：默认只做排版与风格优化，不改变内容含义。
