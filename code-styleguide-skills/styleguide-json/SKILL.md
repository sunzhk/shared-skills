# JSON Code Style Skill

## 目标

基于 Google JSON Style Guide，为 JSON 请求/响应与 JSON 文档提供可执行的风格约束，用于：

- Code Review：快速识别字段命名、值类型、结构组织、可演进性与兼容性问题。
- 风格统一：在不改变接口语义前提下减少“字段风格漂移”和跨服务不一致。
- 输出建议：将规范落到“检查点 + 最小示例”，避免抽象化建议。

## 规范来源与优先级

1. 项目/团队既有 API 约定（版本策略、错误模型、分页模型、兼容策略）。
2. 本 JSON skill（本文）。
3. Google JSON Style Guide（jsoncstyleguide.xml）。

当冲突或无法确定时，默认选择：更兼容、更可读、更易于客户端稳定消费的一侧，并说明理由。

## 核心检查清单（可执行）

### 基础规则（General）

- **禁止注释**：JSON 对象中不得出现注释；示例注释仅用于文档说明，不可进入实际 payload。
- **统一双引号**：属性名与字符串值必须使用双引号；布尔、数字、`null` 不加引号。
- **语义优先建模**：避免仅为“展示方便”随意分组；扁平化与结构化按语义选择。
- **空值处理一致**：可选字段为 `null`/空时，优先评估是否直接省略字段（除非有明确语义）。

### 字段命名（Property names）

- **命名可读且可解释**：字段名应表达明确业务语义，避免无意义缩写。
- **统一 camelCase**：普通属性使用 camelCase ASCII 名称，避免保留关键字与歧义名。
- **数组字段优先复数**：数组字段使用复数命名，非数组通常使用单数命名。
- **Map key 规则分离**：对象作为 map 时，key 不强制遵循属性命名规则，但需在文档中声明该对象为 map。

### 值类型与格式（Property values）

- **值域受限于 JSON 规范**：仅允许对象、数组、字符串、数字、布尔、`null`。
- **枚举值用字符串**：枚举字段优先字符串，增强前后兼容与客户端容错。
- **时间使用标准格式**：日期时间采用 RFC 3339 字符串。
- **时长/地理坐标格式标准化**：时长采用 ISO 8601；经纬度采用 ISO 6709 推荐格式。

### 结构与保留字段（Structure & reserved names）

- **顶层语义清晰**：顶层字段职责明确（如版本、上下文、数据、错误），避免“万能对象”。
- **`data` 与 `error` 互斥**：响应中二者不得并存；若并存应以错误对象优先并尽快修正协议。
- **保留字段慎用**：对约定字段名（如 `items`、分页/链接字段）按既定语义使用，不重载含义。
- **冲突通过重命名或版本化解决**：新增字段与保留语义冲突时，不破坏旧语义，优先改名或主版本升级。

### 可维护性与演进（Evolution）

- **新增字段默认可选**：避免强制旧客户端立即适配，降低升级风险。
- **排序要求仅在必要时执行**：普通 JSON 字段顺序非强约束；仅在协议要求时维护特定顺序。
- **示例与文档同步**：示例 JSON 应可直接映射到协议语义，避免“示例能看不能用”。

## 最小示例

### 双引号与值类型

```json
{
  "name": "bart",
  "age": 10,
  "isStudent": true,
  "nickname": null
}
```

### 数组复数命名 + 枚举字符串

```json
{
  "items": [
    {"id": "1", "status": "ACTIVE"},
    {"id": "2", "status": "DELETED"}
  ]
}
```

### `data` / `error` 互斥（推荐响应形态）

```json
{
  "apiVersion": "2.0",
  "data": {
    "id": "12345"
  }
}
```

```json
{
  "apiVersion": "2.0",
  "error": {
    "code": 404,
    "message": "File Not Found"
  }
}
```


## 工程化落地（Workflow）

- **本地一致性**：提交前至少执行格式化与静态检查，避免仅在 CI 暴露风格问题。
- **CI 守门**：将风格检查作为必过项；格式化工具输出与审查结论冲突时，以团队约定优先并在 PR 说明。
- **渐进整改**：遗留代码按“触达即治理”原则处理，优先修复当前变更范围内的风格/可读性问题。

## 常见冲突与处置

- **规范冲突**：优先级始终为“项目约定 > 本文 > 官方参考”。
- **工具与人工结论冲突**：优先保证可读性与一致性，并在评审中记录取舍理由。
- **增量与全量冲突**：优先保证本次修改范围一致，避免在无关区域引入大规模格式噪音。

## 工程化命令（本地/CI）

- 本地：`prettier -w "**/*.json"`
- CI：`prettier -c "**/*.json"`

## 本 skill 的回答方式（输出模板）

当用户给出 JSON 文档、API 请求/响应示例或字段设计问题时，按以下结构输出：

1. **适用范围判定**：JSON 文档 / API 协议字段 / 响应结构问题。
2. **结论（3-10 条检查点）**：先指出兼容性与语义风险，再给命名/格式一致性问题。
3. **最小修正示例**：提供最小 before/after，确保不引入无关改动。
4. **兼容性声明**：默认优先非破坏性修正；涉及破坏性变更时明确给出版本化建议。
