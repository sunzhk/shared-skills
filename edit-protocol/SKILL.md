# reliable-edit

## 目标

本技能的目标只有一个：

**显著降低编辑失败率，并减少无效重试。**

这里的“失败”包括但不限于：

- 找不到要替换的旧内容
- 命中多个位置，无法唯一定位
- 修改到了错误位置
- 前一次写入后，上下文变陈旧，后续补丁连续失败
- 文件被改动了，但结果不符合用户意图
- 改动后结构、格式、语义被破坏

本技能不是解释原理的说明文档，而是一套编辑时必须执行的操作规程。

## 适用范围

本技能适用于所有普通文本文件，不局限于空白敏感格式。

典型场景：

- 代码文件：`kt`、`java`、`ts`、`js`、`py`、`go`、`rs`、`swift`
- 配置文件：`json`、`yaml`、`toml`、`xml`
- 文档文件：`md`、`txt`
- 构建与脚本：`gradle.kts`、`Makefile`、`sh`

本技能解决的是“定位方式不稳定”和“编辑策略切换过慢”的问题，不依赖某一种语言。

## 不适用场景

以下问题不要误归因到编辑技巧：

- 没有写权限
- 工具本身不可用
- 沙箱或权限限制导致不能改文件
- 用户明确要求先给方案、不要动文件
- 文件是二进制、软链接、自动生成产物且不应手工修改

遇到这些情况，先说明限制，再换正确路线。

## 核心判断

编辑失败最常见的根因有四类：

1. **定位不唯一**
   - 目标文本在文件里出现多次
   - 只拿了一行高频文本做锚点
   - 只匹配字段值、返回值、标题文字等通用片段

2. **上下文过期**
   - 先前读过文件，但中间已经有其他改动
   - 连续补丁建立在旧上下文上
   - 格式化、自动排序、自动补全改变了文件结构

3. **锚点层级过低**
   - 本来应该按“函数 / 类 / 配置对象 / 章节”定位
   - 却只按“某一行文本”定位

4. **策略切换不及时**
   - 失败一次后继续同类重试
   - 明明适合整块替换，却还在做脆弱单行补丁
   - 明明适合程序化改写，却还在依赖裸字符串

## 核心规则

### 规则 1：每次编辑前重新读取目标文件

禁止凭记忆直接构造补丁。

至少确认：

- 文件当前内容
- 目标位置真实存在
- 目标结构的边界
- 是否有重复片段
- 是否已有其他改动

如果没有重新读取文件，就不要编辑。

### 规则 2：先识别结构层级，再决定怎么改

编辑前先判断目标属于哪个层级：

- 单个值
- 单行
- 段落
- 列表项
- JSON 对象
- Markdown 章节
- 函数
- 类
- 配置块
- target / task / rule

优先在“目标所属的结构层级”上编辑，不要默认按单行编辑。

示例：

- `kt` 文件里优先按函数、类、代码块编辑
- `json` 文件里优先按对象字段块、数组项编辑
- `md` 文件里优先按标题下的整段或整节编辑

### 规则 3：锚点必须稳定，且尽量唯一

优先级从高到低：

1. 唯一结构名
2. 唯一结构名 + 局部内容
3. 目标前后相邻的结构化上下文
4. 裸单行文本

默认不要使用裸单行文本作为锚点，特别是：

- `enabled: true`
- `return ""`
- `## Summary`
- `"name": "xxx"`
- `}`、`]`
- 常见 bullet 文本
- 普通日志字符串

### 规则 4：优先改完整逻辑块或完整结构块

以下做法通常比单行替换更稳：

- 用完整函数块替换函数内部逻辑
- 用完整 JSON 对象块替换对象字段
- 用完整 Markdown 小节替换章节内容
- 用完整配置段替换某个配置块

除非目标天然唯一且范围极小，否则不要默认做脆弱单行替换。

### 规则 5：写入后，旧上下文立即失效

只要发生过一次写入，后续任何补丁前都要重新读取，不要沿用旧片段。

这条规则对以下文件尤其重要：

- `kt` / `java` 被 formatter 调整
- `json` 被重排或重格式化
- `md` 被整理标题或列表间距
- `gradle.kts` 被 IDE 自动补全

### 规则 6：第一次失败就诊断，第二次失败就换策略

第一次失败后必须检查：

- 目标是否还存在
- 是否有重复命中
- 锚点是不是太弱
- 结构层级是不是选错了
- 文件是否已变化

第二次失败后必须切换策略，不要第三次继续硬试。

可切换方向：

- 从单行替换改为整块替换
- 从局部字符串匹配改为按结构边界重写
- 从连续小补丁改为一次性重写目标结构
- 从文本级编辑改为脚本或程序化编辑
- 文件较小时改为整文件重写

## 标准工作流

### 第一步：重新读取文件

必须完成以下动作：

1. 读取目标文件
2. 找到目标结构
3. 确认边界
4. 判断是否重复
5. 判断是否已有其他改动

### 第二步：识别目标结构

按真实结构来定位，而不是按“我想改哪句话”定位。

#### Kotlin

优先锚点：

- `fun updateUser(...)`
- `class UserRepository`
- `companion object`
- 唯一属性声明附近的完整代码块

#### JSON

优先锚点：

- 顶层 key
- 某个对象完整字段块
- 某个数组元素的唯一标识字段
- 相邻字段组合

不要只锚定高频值，比如 `"enabled": true`。

#### Markdown

优先锚点：

- `##` / `###` 标题
- 标题下完整小节
- 唯一列表项附近的连续块
- 独特段落首句

多个同名标题并存时，增加更上层标题或相邻内容做锚点。

#### 其他文本文件

优先寻找“结构名 + 局部内容”的组合，而不是直接改短字符串。

### 第三步：选择策略

#### 策略 A：结构块替换

适用：

- Kotlin 函数内部逻辑修改
- JSON 某个对象调整
- Markdown 某节整体改写

这是默认首选策略。

#### 策略 B：唯一锚点 + 局部块替换

适用：

- 只改结构中的一小部分
- 但目标文本本身不唯一

#### 策略 C：结构化插入

适用：

- 在某个标题后插入内容
- 在某个对象中新增字段
- 在某个函数后新增函数

不要靠模糊的短字符串决定插入位置。

#### 策略 D：程序化改写

适用：

- 批量替换
- 结构重复很多
- 文本补丁脆弱
- `json` 更适合用结构化工具处理

#### 策略 E：整文件重写

适用：

- 文件较小
- 修改范围大
- 多次局部补丁不稳定
- 已完整掌握文件内容

使用前要确认不会覆盖用户的并发改动。

## 按文件类型的补充规则

### Kotlin / Java / TypeScript

- 以函数、类、代码块为编辑单位
- 不要只改一行返回值，除非有足够上下文
- 相似函数并存时，必须用签名区分

### JSON

- 优先编辑完整对象或数组项
- 新增字段时，锚定相邻唯一键
- 如果字段顺序重要，改后重新读取确认结构

### Markdown

- 优先按标题小节编辑
- 列表修改时，尽量带上前后条目
- 多个同名标题时，增加更上层标题做锚点

### Python / YAML / Makefile / Shell

- 除了结构定位，还要额外检查空白、缩进、tab、换行
- 这是额外风险，不是本技能的唯一重点

## 失败诊断

### 情况 1：找不到目标

说明你匹配的不是当前文件真实内容。

处理方式：

- 重新读取文件
- 从文件中重新提取真实代码块或文本块
- 提高锚点层级
- 放大上下文范围

### 情况 2：命中多个位置

说明锚点不唯一。

处理方式：

- 加结构名
- 加相邻唯一字段、标题、签名
- 从单行升级为结构块

### 情况 3：改错位置

说明虽然命中了，但锚点设计错误。

处理方式：

- 用更高层级结构重新定位
- 不再依赖短文本
- 改为替换完整目标块

### 情况 4：前一次改动后，后续补丁连续失败

说明上下文已陈旧。

处理方式：

- 重新读取最新文件
- 基于最新内容重新生成补丁
- 不要复用之前的旧内容

## 编辑后校验

每次编辑后至少做两件事：

1. 查看 diff，确认只改了目标位置
2. 做最小合法性检查

按类型补充：

- Kotlin / Java：编译或最小语法校验
- JSON：结构合法性校验
- Markdown：标题层级、列表结构、链接文本检查
- Python：语法检查
- YAML：结构合法性检查

如果无法验证，必须明确说明。

## 输出要求

执行编辑任务时，输出应简短且包含以下信息：

1. 本次修改的目标结构是什么
2. 使用了什么锚点
3. 采用了什么编辑策略
4. 是否遇到失败以及如何切换
5. 做了哪些验证
6. 剩余风险是什么

优先报告操作结论，不要长篇展开原理。

## 禁止事项

- 禁止凭记忆直接改文件
- 禁止默认裸单行替换
- 禁止失败后重复同类尝试
- 禁止在前一次写入后继续使用旧上下文
- 禁止不看 diff 就结束
- 禁止把结构化问题降级成字符串碰运气
